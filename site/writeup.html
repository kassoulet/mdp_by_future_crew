How MDP was reversed and ported

The program

MDP.EXE (Future Crew, 1993) is a Turbo Pascal program linked with STMIK, a Sound Blaster / Gravis driver library, plus two hand-written assembly units: one draws the menu, one draws the playing screen. v1.0 is LZEXE-packed, v1.1 adds volume and mono/stereo keys. The three discs share two executables.

Method

  1. Unpack with unlzexe, disassemble with Capstone, find the units from the far-call targets.
  2. Build an oracle: the original machine code run in Unicorn with a planar VGA model, keyboard and DOS file stubs. Its frames are pixel-identical to DOSBox-X.
  3. Port a routine to JS, then compare planes, CRTC registers and DAC against the oracle on every vsync. The menu matches on all 455 frames of a scripted run. The playing screen's static parts match a DOSBox capture.

Tricks worth a look

Colours are bit planes

Mode 12h has four bit planes. MDP never writes "a colour": it ORs (menu) or AND-clears (playing screen) glyph bits into one plane, and a palette made for that turns plane combinations into the look it wants. The header is colour 15 (all planes set); text is "plane c cleared", so a glyph costs one read-modify-write per row. Drop shadows are the same glyph OR-ed into plane 3, shifted two pixels and two rows.

Sub-byte glyph placement with SHRD

mov  ax, [si]        ; 16-bit glyph row
xor  dh, dh
shrd dx, ax, cl      ; bits pushed off the right edge land in DH
...                  ; shr ax,cl ; xchg ah,al ; or [es:di],ax ; or [es:di+2],dh

One shrd produces the spill byte of a glyph at any x offset, so a row is a word store plus a byte store.

Smooth menu scrolling with the CRTC

The menu lives in a 512x1024 virtual screen (CRTC offset 32, start address = y*64). Scrolling changes the start address; when the window would run past the end of video memory, the line compare register (0x18 plus bit 8 in register 7 and bit 9 in register 9) restarts the display at address 0, so the page wraps for free. The scroll speed ramps up in the first half of the move and down in the second.

Unrolled row fills

A highlight row is 32 word stores in a row, no loop: 64 bytes at 512 pixels. The marker grid is a 386-store unrolled column drawn 39 times.

A bug kept on purpose

The note quantiser has cmp ax,0x3d60 where the table logically wants 0x5d60. It only matters for notes that fall between two semitone boundaries, so the port keeps it.

Audio

The original mixes with STMIK. The port renders with libopenmpt (WebAssembly, in an AudioWorklet). Hi-fi mode uses windowed-sinc interpolation at the browser rate. Old-school mode renders without interpolation at 22.05 kHz, quantises to 8 bits and holds samples, close to a Sound Blaster Pro.

The coloured markers on the playing screen come from STMIK's internal channel state, which libopenmpt does not expose. The port rebuilds instrument, volume and pitch from the pattern data row by row, so portamento and vibrato do not move the markers.
